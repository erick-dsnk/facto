# Optional typed applicability adapter: independent review

This is an unwired design addendum, written after the original mechanism/corpus manifest. Do not rewrite that manifest's frozen files to imply this was an earlier reviewed design. No implementation or provider call is authorized here.

A fixed typed applicability item per authenticated record, added to the existing judgment call, can replace the hand-authored ClaimFrame dependency as an inference adapter. Deterministic code must first validate the installed receipt, its trusted canonical snapshot and exact retained-quote/material-span alignment. It must also enforce revocation, effective period and current-version proof expiry. Jev cannot create authority, install a receipt, select a new trusted version or repair missing record contents.

The applicability item receives the exact admitted claim and retained passage, plus separate trusted server metadata describing the bounded relation, referent, material conditions, version and temporal limits. The passage stays untrusted. Bind its answer to exact claim/excerpt/receipt/version hashes. Permit only covered/not_covered/uncertain; missing, malformed, contradictory or insufficiently confident answers return unavailable. Freeze the acceptance confidence threshold before outputs, independently of verdict thresholds. Keep existing content, directness, scope, stance, probability, risk, selected-citation and full-pool conflict/dependence guards.

The item asks whether the asserted proposition concerns the same permitted record relation and material circumstances, regardless of agreement with its compared value. Counterfactual award/event date, numeric value or defined term can remain covered. A different event verb, reporting period, population, jurisdiction, edition, condition or subject cannot. The receipt grants no factual stance or probability.

The remaining temporal boundary must be stated honestly: deterministic receipt freshness cannot determine what a natural-language claim means. Current versus historical interpretation becomes part of the learned applicability gate. The initial snapshot-only route should require explicitly applicable historical/versioned scope, returning unavailable for unrestricted or implicit-current claims. Current/latest claims additionally require deterministic current-version proof; a timestamp or matching excerpt cannot supply that proof. A future implementation must bind that proof to an inspected artifact/hash and its effective/recheck interval, not trust lastCurrentVersionCheck as a bare string.

Use the independently frozen 22-unit applicability corpus as OPEN development calibration. Add prospectively authored independent controls before integration: implicit present tense, now/latest/deictic dates, ambiguous dates, event date as compared value versus edition/reporting period as material scope, negation, ordinal omission, clipped exceptions, event-verb substitution, wrong population and expired version proof. Pair supported/refuted values for the same relation and require identical capability eligibility. Require zero hard-negative false capabilities and preserve the declared corpus denominator, uncertainty and source-proof limits. Small perfect results do not establish general safety or useful backend coverage.

Adding questions changes context and resource use even without another call. Check serialized request bytes, token accounting/reserves, question-ID binding and output limits; keep the original budgets. Evaluate every full-context assessment and downstream policy output, including excluded ambiguity sentinels, for newly unsupported definitive results. Do not infer an improvement solely from target applicability scores or known world truth. Integration requires a separately reviewed frozen candidate and source/citation audit; this proposal is not production promotion.
